## 作ったもの

- `pipeline/parse.py`（コミット `cca6ec93`）: 塊1（pipeline.discovery）が取得した書類の原形（zip）を解析し、v2 データセットの Silver へ追記する。GitHub Actions のジョブ分割に対応する3段階＋運用サブコマンドで構成する。
  - plan: 取得目録（acquisition/）と書類目録（catalog/）を月をまたいで読み、未解析の zip から計画（plan.json）を作る。対象の特定は提出日（submitDateTime）で行う。解析済みの判定は、解析目録（parse/month=YYYY-MM/ledger.jsonl）の最新行が ok で、入力 zip の SHA-256 が取得目録と一致する場合だけとする。
  - shard: arelle（版は 2.47.5 に固定）で .xbrl インスタンスから数値事実を抽出する。固定事項2点（期間の終端は endDate、プログラムからの利用では FormulaOptions を設定）を実装に入れた。抽出は開示制度による読込遮断を無効にして行い、検証とは分離した。提出者拡張タクソノミの表示名（日英）も DTS から併せて取得する。
  - 検証: EDINET 専用プラグインを、書類の zip に対する公式の呼び出し方（CntlrCmdLine、`--plugins validate/EDINET --disclosureSystem <制度> --validate`）で別プロセスで実行する。開示制度は書類のタクソノミ年度で選ぶ（2025-11-01 版は EDINET、2024-11-01 版は EDINET-2025）。構造系コード（EC01xx）は書類の所見として扱わず検証の実行記録（コード別件数）としてのみ残し、表紙系コード（EC1001E・EC1057E）は年度が合う場合に限り所見として記録する。指摘はすべて記録のみで、取り込みは止めない。
  - 取り込み停止の判定規則（仕様 §2 の 2026-11-17 の決定どおり）: 止めるのは (a) arelle がインスタンスを読めない場合（zip が壊れている、.xbrl が無い、読込に失敗する、取得目録のハッシュと実物が一致しない）と、(b) 抽出できた数値事実が 0 件の場合だけとする。(b) の根拠: 本工程の対象はすべて xbrlFlag=1 であり、バックフィル済みの全書類種別・311,786 件で Silver の行数が 0 の書類は 0 件だった（実測）。止めた書類は書類単位で隔離し、理由を解析目録に記録する（全体は止めない）。
  - merge: shard の結果を集め、月別の silver.parquet へ書類単位の置き換え＋追記で反映してから、解析目録・表示名・実行サマリを push する（データが先、目録が後の規律は塊1と同じ。途中で落ちても次回が冪等にやり直せる）。訂正の系譜（superseded_by）は工程1の確定規則と同一（doc_type=130 のみを訂正とし、同一親への訂正が複数ある場合は提出日時が最も新しい1件、同点なら doc_id の大きい方）で、親書類の行も必要なら書き換える。
  - 表示名の置き場所: 既存 Silver の実物（silver/month=YYYY-MM/silver.parquet）には表示名の列が無いため、Silver へは入れず、P2-T10 の要素辞書への受け渡しとして parse/month=YYYY-MM/extension_labels.jsonl に分けた。
  - repair-lineage（サブコマンド）: 指定した書類の superseded_by を系譜の規則で決め直す運用コマンド（下記の修復で使用）。
- `.github/workflows/daily_parse.yml`（コミット `cca6ec93`）: 日付・書類 ID・上限を指定して手動 dispatch できるワークフロー。plan → parse（マトリクス分割。タクソノミのキャッシュは actions/cache でジョブ間に共有し、検証の別プロセスも同じキャッシュを使う）→ merge の構成。arelle は parse ジョブでのみ 2.47.5 を固定して入れる。
- `.github/workflows/lineage_repair.yml`（コミット `cf180ecb`）: repair-lineage の実行用ワークフロー。

## 試験と実測

1. **等価性（標本照合）**: S2-T3 の標本45書類のうち8書類（S100XRPR 1,432 件、S100XTLJ 941 件、S100MQHX 315 件、訂正ペア S100Y335・S100W0ZR 各 2,518 件、S100TV7A 1,307 件、実体参照の壊れた S100PYBK 24 件・S100PY3F 23 件、合計 9,078 事実）で、新しい解析経路の出力と既存 Silver を S2-T3 と同じ照合規則（要素・期間・次元・単位・値の多重集合）で突き合わせ、全件一致した（欠落 0・余分 0・値違い 0）。壊れた2書類は arelle の回復で読め、隔離されなかった（既存 Silver の扱いと同じ）。
2. **隔離（ローカル）**: 切り詰めた zip は bad_zip、.xbrl を抜いた zip は no_xbrl_instance、事実が無い最小のインスタンスは process_document 経由で zero_facts として、それぞれ隔離されることを確認した。検証の動作確認では、S100XRPR で年度に合う制度（EDINET-2025）が選ばれ、構造系が実行記録にのみ残り、表紙系が 0 件になることも確認した。
3. **実地（2026-11-16 分）**: いずれも daily_parse の手動 dispatch で、開始時刻は UTC。
   - dispatch 1（01:33:13Z 開始、date=2026-11-16、max_docs=30）: **success**。30 書類すべて ok で、2,087 行を silver/month=2026-11 へ追記した（864,034 → 866,121 行、書類数 4,112 → 4,142）。HF 側で解析目録 30 件・表示名 52 行・実行サマリの実在を確認し、parquet 内の書類ごとの行数が解析目録と全件一致した。検証は 30 件すべて実行され（タクソノミ年度に合う制度があったのは 23 件、残り 7 件は制度が無い版を参照するため EDINET で実行し表紙系をノイズとして扱った）、指摘はすべて記録のみで取り込みは止まらなかった。
   - dispatch 2（01:52:12Z 開始、doc_ids=S100ZHJA）: **success**。訂正書類（doc_type=130）1,797 行を取り込み（point_in_time=final、parent_doc_id=S100YTII）、親書類 S100YTII（silver/month=2026-07）の superseded_by が S100YZGY から S100ZHJA へ更新されたことを実物で確認した。
   - dispatch 3（01:56:16Z 開始、dispatch 1 と同条件）: **success**。計画は未解析分から作られるため次の 30 書類が対象になり、全件 ok。解析目録は 61 件になり、parquet（870,880 行）の書類ごとの行数は目録と全件一致した（二重取り込みなし）。
   - dispatch 4（02:02:45Z 開始、解析済みの 3 書類を指定）: **success**。計画の対象が 0 件となり、parse と merge は skipped になった（冪等）。
   - 申し送りの対象外: 提出日の異なる 10 件（取得目録は ok だが原形の実体が HF に無いもの）は、計画が提出日で対象を絞るため今回の解析対象に入っていない。回復は塊1 修正の着地後の再 dispatch で行う範囲である。

## 途中で見つけて直した問題

1. **系譜の訂正判定の範囲（自分の実装の欠陥）**: 初版は parent_doc_id を持つ全種別を訂正として扱い、dispatch 1 で 040（訂正有価証券届出書）2 件の親（S100WUM6・S100XX97）の superseded_by を、工程1の確定規則（doc_type=130 のみ）では付かない値に書き換えてしまった。コミット `cf180ecb` で判定を 130 のみに限定し、repair-lineage で両書類を null へ修復した（修復の実行は 01:48:59Z 開始、success）。修復後、silver/month=2025-11（1,217,832 行）と month=2026-05（496,714 行）の parquet がバックフィル状態と全表一致することを確認した。
2. **repair-lineage の自己確認（自分の実装の欠陥）**: 初版は現在の superseded_by を勝者の候補に含めたため、修復が「現在の値が正しい」という自己確認になって何もしなかった。コミット `81396c25` で、現在の値は解析目録で doc_type=130 と分かる場合だけ候補に含めるよう直した。あわせて、証跡保存（tee）が work/ 未作成で失敗する問題を両ワークフローで直した（修復の初回実行 01:40:18Z 開始がこの失敗に当たった）。
3. **着地の競合**: 修正の途中で塊1 修正の PR #30 が main へ入り、fast-forward が拒否されたため、現在の main の上にコミットを作り直して着地した（`81396c25`）。このためブランチ s2-t5-parse は旧コミット（`e95339e3`）を指したままになっている（force 更新はガードで不可）。正は main である。main のテスト CI（tests.yml）は着地後の push で success を確認した。

## 残した未決事項

- 検証の部分実行: arelle 2.47.5 の rule_EC8021W が AttributeError で落ち、検証の別プロセスが終了コード 1 を返す書類がある（実測は S100XRPR）。ログに残った指摘は実行記録として有効なため、解析目録では partial として記録する扱いにした。検証は記録のみであり、取り込みへの影響はない。arelle の版更新時に再確認すること。
- 年度に合う開示制度が無いタクソノミ版（プラグインの制度は 2024-11-01 版と 2025-11-01 版のみ）を参照する書類では、表紙系コードを所見にできない（dispatch 1 の 30 件では 7 件）。制度の追加への追随は P2-T9 の年次確認の範囲。
- 解析目録で quarantined / failed になった書類は、次回の計画で再試行される（batch と同じ扱い）。恒常的に読めない書類が現れた場合の再試行の上限や警報の扱いは、仕様 §5 の監視と合わせて決める必要がある。
- 検証が約 40 秒/書類と処理時間の支配項である。1 日分の全件（数百件）を回したときの所要時間は、タクソノミキャッシュの効きと合わせて本運用（cron 化）の前に実測すること。
- cron のスケジュール有効化、コードリストの差分（§4）は後続の塊の範囲。EDINET API のレート制限の実測は取得側（塊1）の事項であり、本塊は EDINET API を叩かない。
