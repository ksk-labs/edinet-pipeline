# 工程2 P2-T4 会社イベントと親子関係 — 作業記録（設計と実施結果）

Issue: ksk-labs/edinet-pipeline #19（P2-T4）。仕様: files/2026-11-16-step2-phase2-spec.md §5（Issue #15）。
状態: 実施済み（2026-11-17）。配置はマージ後にワークフローを dispatch して行う（本記録の「配置について」参照）。

## 範囲

- 仕様 §5 のうち、会社イベントの器と臨時報告書分の取り込み、親子関係の
  時点つき記録を実施した。
- プログラムは pipeline/company_events.py、運用ワークフローは
  .github/workflows/company_events.yml（新規）、テストは
  tests/test_company_events.py（新規24件）。
- 成果物は v2 データセットの master/ 配下に置く:
  company_events.parquet（会社イベント）、company_relationships.parquet
  （親子関係）、company_events_summary.json（構築サマリ）。

## 実測と、取れる信号・取れない信号の切り分け

設計に先立ち、v1 索引（477,025行）と実物の書類で信号を切り分けた。

### 取れる信号（メタデータ）

- 臨時報告書（v1 索引の doc_type=180、対象期間 35,807件）の
  current_report_reason に、提出事由が府令の条項として構造化されて
  入っている。複数事由はカンマ区切りで複合する（原子の延べ 37,329 件）。
- 対応表は一次情報から作った: e-Gov で公表されている
  企業内容等の開示に関する内閣府令（昭和48年大蔵省令第5号、
  law_id 348M50000040005）第19条第2項と、特定有価証券の内容等の
  開示に関する内閣府令（平成5年大蔵省令第22号、law_id
  405M50000040022）第29条第2項の現行条文（2026-10-05 施行の改正まで
  反映された版）の各号の文面である。観測された原子は全件が対応表に
  載り、分類できないのは「第19条の2」（別条の事由、対象期間 22 件）
  のみだった。これらは未分類（unclassified）として原子の原値を保持する。
- 親会社等状況報告書（doc_type=200、同 757 件）は、提出者が親会社等、
  subsidiary_edinet_code が上場子会社を指し、そのまま親子関係の
  観測になる。訂正（doc_type=210、84 件）は全件が原書類と同じ
  子会社コードを指していた（実測）。
- 書類メタデータの issuer コードは大量保有報告書系（doc_type=350・360）
  にしか現れず、subject コードは公開買付け関係書類系にしか現れない
  （対象期間の全件で実測）。この2系統は本チケットの範囲外であるため、
  関係の投入もその取り込みチケットに合わせる。
- 提出事由が空の臨時報告書は 425 件で、xbrl_flag が偽の件数と一致する
  （XBRL の無い書類では事由が索引に載らない）。これらは未分類の
  イベントとして、書類の存在自体は年表に残す。

### 取れない信号（書類本文）

- 実物の臨時報告書（様式第5号の3、jpcrp050300-esr）の XBRL を標本で
  確認した。本文は事由ごとのテキストブロック（例:
  ChangesInParentCompaniesOrSpecifiedSubsidiariesTextBlock、
  DecisionOnHoldingShareholdersMeetingForPurposeOfReverseStockSplit
  TextBlock）に自由文で入っており、相手先の名称、異動の年月日、
  株式併合の割合・効力発生日は決まった書式を持たない（年月日が
  「2026年12月（予定）」のように月単位の予定で書かれる例も実在する）。
  相手先は未上場の子会社等が中心で EDINET コードも無い。
- したがって本チケットでは、本文由来の構造化抽出は行わない。器には
  related_edinet_code / related_internal_id / event_date /
  split_ratio / effective_date の列を用意し、null のまま残す。
  抽出はテキスト層の本格実装（別工程）の範囲とする。誤った抽出を
  年表に載せるより、欠けたままであることを明示する方を取る。
- 株式分割には府令に独立の号が無い（株主総会の決議事項として
  第9号の2の本文に埋もれる）ため、EDINET の範囲では系統的な源泉が
  無い。種別 stock_split は予約のみとし、株式併合は第4号の4から
  取り込む（割合・効力発生日は上記のとおり null）。

## 設計判断と根拠

- イベントの単位は (源泉書類, 提出事由の原子) とした。1書類が複数
  事由を持つ場合に、事由ごとに年表へ載せるためである。event_id は
  doc_id と原子の位置から決定的に作る（再構築で同じ ID になる）。
- イベントの日付は開示日（提出日時）とした。本文中の発生日は
  決定的に取れないためであり、発生日用の列（event_date）と分けて
  区別する。年表の並びは開示日で一意に決まる。
- 訂正臨時報告書（1,450 件）は新しいイベントとして数えず、原書類の
  イベントに一本化した。訂正の件数はサマリに残す。親会社等状況報告書
  の訂正も同様に観測として二重に数えない。
- 親子関係は (親会社, 子会社) 単位に集約し、初回・最終の観測日と
  観測回数、最初と最後の源泉書類を持つ形にした（識別子履歴の観測の
  持ち方と揃えた）。提出者と子会社が同一コードの組が 5 組実在し、
  事実として保持したうえでサマリに self_pairs として数えた。
- イベント種別には株主優待の新設・変更・廃止を予約した（生成しない）。
  主たる源泉は TDnet で、取り込みは TDnet フェーズである（仕様 §5）。
- 対象範囲は提出日 2021-11-01 以降（第1期 Silver の範囲）とした。
- ワークフローは company_master.yml への相乗りではなく新規
  （company_events.yml）とした。根拠: company_master はコードリストの
  スナップショット駆動であり、本チケットは v1 索引と会社マスタを
  入力とする別系統の再構築であること。モジュールごとにワークフローを
  分ける形は extension_dict.yml の前例とも一致する。配置先が master/
  で共通するため、成果物の命名は company_master の流儀に揃えた。
- doc_type の注意: v1 索引の doc_type は API の docTypeCode と一部
  異なる独自番号であり、タイトルで実測して対応を確認した（180 =
  臨時報告書は API と同じ。親会社等状況報告書は v1 で 200、API では
  300）。本モジュールは v1 索引を入力とするため v1 の番号を使う。

## 実施結果（ローカル実行、2026-11-17、v1 索引の固定版で実測）

- 会社イベント: 37,751 件（臨時報告書 35,807 件から生成。
  訂正 1,450 件は除外しサマリに計上）。提出者の内部 ID は全件解決した
  （未解決 0）。未分類は 447 件（事由なし 425 件＋「第19条の2」22 件）。
- 種別の主な内訳: 特定期間の満了 11,534、株主総会の決議 11,242、
  財政状態等に著しい影響を与える事象 2,597、親会社・特定子会社の
  異動 2,107、連結の同種事象 1,829、株券等の取得勧誘 1,719、
  主要株主の異動 1,747、代表者の異動 1,163、子会社取得 431、
  吸収合併 185、株式交換 160、株式の併合 194、解散・信託の終了 361。
  全内訳は company_events_summary.json にある。
- 親子関係: 298 組（親会社等状況報告書 757 件の観測から集約。
  訂正 84 件は観測に数えない）。内部 ID は親・子とも全件解決した。
- テスト: 新規 24 件を含む全 174 件が合格（CI でも確認する）。

## 配置について

- 配置の経路は .github/workflows/company_events.yml（手動 dispatch、
  command は build のみ）。ワークフローはデフォルトブランチに
  着地して初めて dispatch できるため、実際の配置は本 PR のマージ後に
  行う。マージ後の手順は (1) company_events ワークフローを dispatch、
  (2) master/company_events_summary.json の件数が本記録の照合値と
  一致することを確認、の順である。
- 本記録の照合値は、同じプログラムをローカルで実行した結果である
  （入力は v1 索引の固定版と、配置済みの master/edinet_codes.parquet。
  generated_at のみ実行ごとに変わる）。

## 残件・限界

- 本文由来の構造化（株式分割・併合の比率と効力発生日、相手先の同定、
  異動・効力発生の年月日）は未実施で、器の列は null のままである。
  テキスト層の本格実装（別工程）で扱う。
- 株式分割の系統的な源泉は EDINET には無い。TDnet フェーズで
  適時開示を取り込む際に stock_split の生成を始めるのが自然である。
- 親子関係の追加の源泉（公開買付け関係書類・大量保有報告書からの
  関係、有報の関係会社の状況）は、それぞれの取り込みチケットと
  テキスト層（P2-T7）の範囲として残る。本チケットで投入したのは
  親会社等状況報告書分のみである。
- 臨時報告書の第3号（親会社・特定子会社の異動、2,107 件）はイベント
  として取り込んだが、相手先が本文の名称のみでコードが無いため、
  関係の辺にはしていない。
- 日次の差分更新（v2 の書類目録からのイベント追加）の配線は本
  チケットに含めない。現行の build は入力全部からの冪等な再構築で、
  日次化は書類目録（S2-T5）側の経路と合わせて後続作業で扱う。
- 対応表は現行条文に基づく。府令改正で号の意味が変わった場合、
  改正前の書類の分類が現行の意味で読まれる留保がある。観測された
  原子はすべて現行条文の号に載っていたため、少なくとも「対応表に
  無い号」は存在しないことを確認済みである。
- 会社の消滅理由と承継先リンク（companies.parquet の器）の裏取りは、
  本チケットのイベントだけでは確定できない（消滅を直接示すメタデータ
  信号が無い）ため、引き続き未確定のままである。
