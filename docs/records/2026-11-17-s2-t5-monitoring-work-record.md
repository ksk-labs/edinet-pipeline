## 作ったもの

### 1. cron の有効化（schedule）

3本の日次ワークフローに schedule を付け、新規の監視ワークフローを加えた。時刻はすべて JST で、根拠は次のとおり。

| ワークフロー | 時刻 (JST) | 根拠 |
|---|---|---|
| daily_acquire | 03:30 と 15:30 の2回 | 下記 |
| daily_parse | 05:30 | 下記 |
| daily_codelist | 09:15 と 15:15 の2回 | 下記 |
| daily_monitor（新規） | 21:30 | 下記 |

- **取得 03:30（1回目）**: EDINET では取下げ等のステータス変化が「取下書提出日の翌日 24 時過ぎ」の日次更新で一覧に反映される（EDINET API 仕様書 (Version 2) 3-1-5）。対象である前日分の観測は、翌日 0 時を過ぎてから取るのが正しい。取得の実測は 2026-11-16 分 416 件で約32分（塊1）であり、03:30 開始なら解析の開始（05:30）までに、schedule の遅延を見込んでも余裕がある。
- **取得 15:30（2回目）**: 1回目の失敗・滞留への同日回復。対象は同じく前日で、冪等なため取得済みは飛ばされる。割り切りとして、その日の新規提出は翌日の1回目で取る（日次バッチであり、速報性は要件にない）。
- **解析 05:30**: 取得1回目の完了見込み（04:30 頃）の後に開始する。対象は date を空にした「未解析の全件」であり、取得2回目で増えた分と前日の取りこぼしは翌日の実行が自動で回収する。所要時間の見積りは後記の実測による。
- **コードリスト 09:15 と 15:15**: 当日分のスナップショットを当日中に確保することが目的（STATE の決定: 1日に複数回、時間をずらして試行し、当日1回の成功で確保）。朝は金融庁の当日分への切替が済んだ後を狙い、午後は切替が遅れた場合の再試行である。日付は CSV の宣言日で決まるため、早く回して前日分が返っても冪等に終わり、害はない。
- **監視 21:30**: その日の全工程の後に、その日の最終状態を点検する。解析の最悪側の見積り（後記）でも夜までには終わる。
- 分の配置はいずれも正時を避けて 15 分・30 分にした（Actions の schedule は正時に集中し、遅延しやすいため）。

### 2. 監視と日次報告（pipeline/monitor.py、新規）

その日の状態を、v2 データセット上の成果物（目録と実行サマリ）から点検し、日次報告 `monitor/reports/date=YYYY-MM-DD/report.json` と状態ファイル `monitor/state.json` を v2 へ保存する。成果物ベースのため、ワークフローが起動しなかった・途中で落ちた場合は「実行サマリが無い」として検知できる。

- 点検項目（仕様 §5 の監視対象に対応）:
  - 取得の失敗: 前日分の実行サマリが無い（acquisition_missing）、または最新のサマリに失敗件数がある（acquisition_failures）。連続失敗の日数を状態ファイルに保持し、日次報告と警報の両方に明示する。同日の再実行では二重に数えない。
  - コードリストの欠落: 当日分のスナップショットが無い（codelist_missing。欠落は EDINET 側に過去分が無いため埋められない旨を警報に併記）。同日・異内容の競合（codelist_conflict）と、差分の未生成（codelist_diff_pending）も警報にする。
  - 検証エラーの隔離件数: その日に隔離・失敗した書類の件数と理由別の内訳（parse_quarantined）。
  - 処理の滞留: 前日以前に取得されたのに未解析のままの書類（parse_backlog）。当日取得分は翌日の解析が正常経路のため数えない。
  - 退避: 連続失敗が上限に達した書類（parse_retired。3. の再試行上限と対）。
  - 件数の健全性信号: コードリストの提出者数、その日の書類一覧の件数、その日に解析できた件数と行数を、日次報告の signals に毎日記録する（警報ではなく記録）。
- 警報があっても監視自体は成功として終わる（終了コードは監視自体の障害でのみ 1）。理由は 5. の判断事項に記す。
- 実データでの読み取り確認: 2026-11-16 分の取得サマリ（1件、失敗 0、一覧 416 件）、2026-11-17 のコードリスト（11,468 行）、解析目録 61 行を実物で読み、判定が例外なく動くことを確認した。HF への書き込みを伴う実地（dispatch）は着地後に行う。

### 3. 隔離書類の再試行上限（pipeline/parse.py）

塊2 の未決事項（隔離・失敗した書類の再試行の上限と警報の扱い）への対応。

- 解析目録の履歴から書類ごとの連続失敗回数（隔離・失敗）を数え、上限 `MAX_PARSE_ATTEMPTS = 5` 回に達した書類は plan の対象から外す（退避）。退避した書類は plan.json の retired に理由つきで残り、監視が parse_retired として日次報告に載せる。
- 書類 ID を明示指定した場合は退避を適用しない（運用側の明示的な再試行を妨げない。これが退避からの復帰経路である）。
- 上限の値の根拠と性格は 5. の判断事項に記す。

### 4. 目録の途中 push（pipeline/discovery.py、Issue #29 の範囲）

塊1 の作業記録の改善事項（目録の push は実行末尾の一括のみ）への対応。

- 書類目録は観測の記録であり原形の実在に依存しないため、一覧の取得が済んだ時点で先に push する。実行がこの後に落ちても、その日の観測は残る。
- 取得目録は、原形のアップロードが保存先ディレクトリ単位で済むたびに途中でも push する。不変条件（目録の ok は、アップロード後に遠隔で実在を確認できた分だけ書く）は維持しており、途中 push の内容についても、push の時点で ok の行の指す実体が遠隔に実在することをテストで固定した。確認できなかった分は保留し、最後にもう一度確認してから ok／failed を確定する。
- 代償: 遠隔のファイル一覧の取得が、保存先ディレクトリの数だけ増える（1日分では提出日×種別で数十回程度。一覧取得は HF 側の1リクエストであり、取得の本体処理に比べて小さい）。

## 実測: 1日分の解析所要時間

検証が支配的だった件（塊2 の未決事項）について、実物の zip で実測した。測定はこの VM（共有 CPU）で、webcache が冷たい状態から逐次処理し、pipeline.parse の実物関数（抽出と検証）を使った。対象は 2026-11-16 提出分の zip からサイズの小・中・大を3件ずつ（計9件）。

- 抽出: 合計 113.0 秒（平均 12.6 秒/書類）。検証: 合計 165.3 秒（平均 18.4 秒/書類）。合わせて平均 約31 秒/書類。
- 初回の書類はタクソノミの取得が入り抽出 19.8 秒。キャッシュが効いた小さい書類は抽出 0.1 秒・検証 1.8 秒まで落ちるため、平均は悲観側の値である。
- 検証の部分実行（partial）は中・大の全件で発生した（arelle 2.47.5 の rule_EC8021W の AttributeError。塊2 で記録済みの既知の問題で、記録のみ・取り込みへの影響はない）。
- 見積り: 1日分の解析対象は、2026-11-16 分の実績で zip 取得 ok 321 件（提出日ベースでは日により変動）。単一プロセス換算では 321 件 × 約31 秒 ≈ 2.8 時間。daily_parse は既定で 4 shard 並列のため、単純に割れば約42分、shard ごとの初期取得を見込んでも 1 時間強が目安になる。timeout（350分）には十分収まる。
- 留保: 測定環境はこの VM の共有 CPU であり、GitHub Actions の標準ランナーとは性能が異なる。絶対値ではなく、cron の時刻配置と timeout の桁の根拠として使う。実績値は cron 有効化後の監視（処理の滞留の検知）で継続して観測できる。

## 判断事項（メインへの報告。いずれも推奨つき）

1. **警報の届け先**: 仕様 §5 の定めは「状態ファイルと日次報告に載せる」までであり、本実装はそこまで。追加の通知手段の選択肢: (a) 現行どおり報告のみとし、7日間の運転で観測する（推奨。監視の存在自体が新しいため、まず見落としの実績を測る）、(b) 警報時に monitor の終了コードを 1 にして GitHub Actions の失敗通知に乗せる（手軽だが、監視自体の障害と警報の区別が付かなくなる）、(c) 警報の発生時に専用の Issue を自動で起票・追記する（状態ファイルと二重管理になる代わりに、目に触れる場所に出る）、(d) メール等の外部通知（宛先と運用の設計が別途要る）。
2. **再試行上限 5 回の値**: 根拠は「一時的な失敗（HF やネットワークの一時障害、キャッシュの破損）は日単位で回復しうるため、営業日1週間分は毎日の計画に載せ、それを超えたら恒常的な問題とみなす」という運用判断である。仕様に由来する数値ではなく、強く裏付けられた値でもない。値を変える場合は parse.py の定数1箇所で足りる。
3. **監視の終了コード**: 警報では終了コードを変えない現行の形は、「監視が落ちて報告自体が無くなる」事態を避けるための選択である。1. で (b) を選ぶ場合はこの判断も併せて変えることになる。
