## 作ったもの

- `pipeline/discovery.py`（コミット `3fc72e9f`）: EDINET API で対象日の書類一覧（type=2）を取得し、次を v2 データセット（Yoshi-Dai/financial-lakehouse-v2）へ保存する。
  - 書類目録 `catalog/month=YYYY-MM/ledger.jsonl`: 一覧の各行を観測として追記する（API の応答の全項目＋出所＝源泉の種別・源泉側の識別子・取得日時・再配布可否）。同じ書類を別の実行で観測すれば行が増え、取下げ等で項目が null に変わる変化も履歴として残る。
  - 一覧の応答そのもの `catalog/responses/date=YYYY-MM-DD/fetched_at=<取得日時>.json`: API が返した JSON をそのまま保存（追記のみ）。
  - 書類の原形 `raw/edinet/YYYY/MM/DD/{zip,pdf,attach,english}/<docID>`: zip（書類取得 API type=1）・PDF（type=2）・添付文書（type=3）・英語開示ファイル（type=4）を原形のまま保存する。CSV（type=5）は取得しない（XBRL からの機械生成の複製のため）。
  - 取得目録 `acquisition/month=YYYY-MM/ledger.jsonl` で取得状態を管理し、「目録が ok で保存先が HF 上に実在する」原形は再取得しない（冪等）。原形のアップロードが済んでから目録を push する。1書類の失敗で全体を止めず、失敗は目録へ理由つきで記録して次回の実行で再試行する。
  - EDINET API のリクエスト間隔は 1.1 秒（v1 の運用実績＝1秒に1回の制限への余裕）。429・5xx・接続エラーは指数バックオフで再試行する。API キーはログと目録に出さない（エラー文字列から除去する）。
- `.github/workflows/daily_acquire.yml`（コミット `8cde3428`）: 日付を指定して手動 dispatch できるワークフロー。date が空なら前日（Asia/Tokyo）を対象にする。schedule のコメントを外せば cron 化できる形にしてある（定期実行の有効化は本塊の範囲外）。

## §1 の残り・申し送り

- コードリストの日次スナップショットと差分は仕様 §4 の範囲で、本塊には含めていない（別の塊で扱う）。
- 目録の push は実行の最後にまとめて行う。大きな日で実行が途中で落ちると、原形は HF に残るが目録が push されず、次回は再取得からになる（upload_folder が同一ファイルを飛ばすため、実害は再取得の時間のみ）。cron 化の前に、バックフィルの push-ledger と同様の途中 push を入れることを検討する。
- 書類あたりの取得時間のばらつきが大きい（dispatch 2 の遅さ）。EDINET API のレート制限の数値の実測（Issue #14 の受け入れ条件の一部）とあわせて、本運用前に原因を切り分けること。現行は v1 実績の 1.1 秒間隔。
- 解析（arelle）と Silver への追記は塊2以降。EDINET 検証の指摘のうちどのコードが Silver への取り込みを止めるかと、合格条件の「7日間」の決め直しは未決事項としてメインへ上げる。
