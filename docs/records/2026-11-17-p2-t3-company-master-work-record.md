## master/ の構成（本チケットで決定し、ここを正本とする）

成果物は v2 データセット（Yoshi-Dai/financial-lakehouse-v2）の master/ 配下に置く。

| パス | 内容 |
|---|---|
| master/history_from_v1/ | P2-T2 の再構成成果（identifier_history、code_roster、code_connections、review_items、summary.json）と、派生集計 last_submissions.parquet（コード×書類種別ごとの最終提出日と件数） |
| master/companies.parquet | 会社（内部 ID 単位）の台帳。status（active / absent）、disappearance_reason、successor_internal_id（いずれも未確定は null。裏取りは P2-T4 の会社イベント側） |
| master/edinet_codes.parquet | EDINET コードと内部 ID の対応（内部 ID の発行台帳を兼ねる）。assignment_basis（initial_v1 / jcn_strong / jcn_corroborated / new_in_codelist）、connected_from、filer_role（提出の立場＝コードリストの提出者種別の現行値） |
| master/identifier_history.parquet | 外部識別子と名称の有効期間つき履歴。v1 再構成の行（source_kind=v1_index）とコードリストの観測行（source_kind=edinet_codelist_download）を源泉を区別したまま併記する |
| master/attribute_history.parquet | 属性（所在地・業種・上場区分・資本金・決算日・連結の有無・提出者種別）の有効期間つき履歴。識別子と同じ開閉の規則 |
| master/securities.parquet | 銘柄レイヤー（会社と銘柄は 1:N）。種類は証券コードの予備コードで識別。is_primary と primary_basis を持つ |
| master/classifications.parquet | 分類体系の版つき参照データ（値ごとに初出日と最終観測日） |
| master/review_items.parquet | 未確定のまま残す項目（P2-T2 の93件を引き継ぎ、更新時にも追加する） |
| master/last_submissions.parquet | 派生属性（源泉の事実ではないことを is_derived で区別）としての内部 ID × 書類種別の最終提出日 |
| master/state.json | 適用済みスナップショットの最終日と次の内部 ID（更新の再開判定） |
| master/summary.json | 構築・更新のサマリと照合結果（接続の照合、コードリストによる裏取り結果を含む） |

有効期間つきの行の規則（識別子・属性に共通）: 同じ値が続けば最終観測日と観測回数を
伸ばし、値が変われば前の行を閉じて新しい行を開く。記録する日付は検知日であり、
実際の変更日とは区別する（仕様 §1）。名称は正規化前（value）と正規化後
（value_normalized、change_key）を併記し、検索は全履歴名称にヒットする前提の形にした。
空文字の属性値（所在地の記載なし等）は観測として記録しない。

## 内部 ID の発行規則

- 初期構築: 法人番号の接続でまとめた組と単独コードに、代表コード（組の最小の
  EDINET コード）の昇順で 1 から連番を発行する。意味は持たせない。
- 更新: 新しいコードには既存の最大値+1 から、コードの昇順に発行する。
  既存の対応は変えない。発行台帳は edinet_codes.parquet 自体であり、
  state.json の next_internal_id と二重に持つ（再開判定用）。

## 法人番号による接続の規則と裏取り

接続の規則は reconstruct_v1 と同じ（strong = 両側複数行かつ両側の多数派、
corroborated = 多数派同士で名称または所在地が一致し証券コードに矛盾がない、
それ以外は要確認）。更新時に新しいコードを判定する際は、蓄積した観測
（v1 再構成＋コードリスト）全体を材料にする。

### 多数派の同数タイの規則（本チケットで決定）

従来の再構成は「観測回数が最大の法人番号」を dict の挿入順で選んでおり、
同数タイの場合に結果が処理順序へ依存する余地があった。本チケットで
決定的な規則として次を定めた: **多数派は、観測回数が最大の値が1つだけの
場合に限る。同数が複数ある場合は多数派なしとして扱い、その法人番号を
接続の根拠にしない（要確認に回す）**。根拠: 仕様 §1 の「多数の観測を
優先する」は、多数が一意に定まる場合にだけ意味を持つ。同数の観測から
片方を選ぶことは、観測に基づかない恣意的な決定になるため、安全側
（未確定として残す）に倒す。reconstruct_v1.majority_jcn と
company_master.majority_value の両方に同じ規則を実装した。

実データへの影響: v1 索引には同数タイのコードが存在しない（複数の法人番号を
持つコードは E05335 と E30091 の2件で、いずれも多数派は一意）ため、
タイ規則を入れた再構成を実データで再実行しても、成果4表はすべて
P2-T2 の検証済み成果と一致した（generated_at を除く全行一致。
履歴24,364行、接続9組＝strong 5・corroborated 4、要確認93件）。

## 銘柄レイヤー

- 種類の識別は証券コードの予備コード（5文字目）を主信号とする
  （0=普通株式、1=新株式、2=第二新株式、5・6=優先株式、3・4・7・8=その他の
  種類株式、9=新株予約権証券。証券コード協議会の取扱い要領）。
  英数字コード（例: 619A0）も5文字目で同じく判定する。
- プレースホルダ 00000 は銘柄として数えず、識別子履歴に観測としてだけ残す。
- 主銘柄（is_primary）は、現行スナップショットにある会社ではその証券コード、
  無い会社では最終観測日の最も新しいコードとし、primary_basis に根拠を持つ。
- 実測（初期構築）: 銘柄は4,494件（普通株式4,492、その他の種類株式2）。
  その他の種類株式は v1 履歴で観測された E36312 の 04018（予備コード8）と
  E36769 の 04364（予備コード4）。複数銘柄を持つ会社は3社（いずれも
  コード変更に伴う新旧コードの併存で、例: 04018 と 40180）。
  コードリストの証券コードは全件予備コードが 0 であり、現行の主銘柄に
  種類株は現れない。これはコードリストが提出者あたり代表の1コードだけを
  載せる性質と整合する。
- 到達範囲の明記: 本チケットの範囲は「器と主銘柄の登録まで」（チケットの
  定め）であり、種類株の同時列挙は EDINET 書類側（有報の種類株式の内容）を
  第一源泉とする後続作業に残る。合格条件3のうち、1:N の表現と予備コードに
  よる種類識別は上記の実データで検証済みであり、種類株を持つ会社の同時
  列挙の検証は書類側の取り込み後に行う。

## 分類体系の版つき参照データ

値域（業種・上場区分・提出者種別・連結の有無）を値ごとの行として持ち、
first_seen_date（初出日）と last_seen_date、snapshot_count を記録する。
ある日付時点の版は、その日付を [first_seen_date, last_seen_date] に含む
値の集合として再現できる（時点つきの参照データとしての「版」の解釈を
ここに記録する）。新しい値はスナップショットの適用時に差分で検知して
初出日とともに登録する。初期構築の実測では50値（業種39、提出者種別7、
上場区分2、連結の有無2）。

## 残件・限界

- ファンドコードと CIK は識別子の種別の器を用意したが、初期投入では
  未投入である。コードリストには無く、v1 索引のファンドコード列は
  P2-T2 再構成の対象外だったため、再構成の成果を変えない範囲では
  取り込めなかった。取り込みは再構成の拡張として後続で扱う。
- 代表者（役職・氏名）はコードリストに無く、有報の文字事実と臨時報告書の
  異動イベントが源泉であるため、本チケットでは属性の器に含めていない
  （P2-T7 のテキスト層の器と P2-T4 のイベントが受け皿になる）。
- 消滅理由と承継先リンクは器（列）を用意した段階であり、値は未確定
  （null）のままである。裏取りは P2-T4 の範囲。
- 最新の提出日（last_submissions）の日次更新は、コードリストではなく
  書類目録（S2-T5）の側の経路で行うものであり、本チケットでは初期値の
  投入までを行う。
- update の日次定期実行への配線（daily_codelist への相乗り等）は
  本 PR に含めていない。初期構築の配置後に運用側で配線する後続作業
  として残す。
- 同じスナップショット回に初めて現れる新規コード同士の接続は、
  先に処理したコードの観測（法人番号1回分）までを材料に判定する。
  両側複数行を要求する strong は新規コード同士では成立せず、
  corroborated の条件を満たさない組は要確認に残る（次回以降の
  スナップショットで観測が増えても、割り当て済みのコードの再判定は
  行わない。これは内部 ID の安定性を優先する判断である）。
