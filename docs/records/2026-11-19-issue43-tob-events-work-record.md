## 実測（v1 索引の固定版、全件集計）

- 公開買付系（v1 索引の doc_type）: 240 公開買付届出書 611 件、
  250 訂正公開買付届出書 497 件、260 公開買付撤回届出書 1 件、
  270 公開買付報告書 594 件、280 訂正公開買付報告書 3 件、
  290 意見表明報告書 477 件、300 訂正意見表明報告書 272 件、
  310 対質問回答報告書 8 件、320 訂正対質問回答報告書 0 件。
- 大量保有系: 350 が 64,284 件（タイトルは5種のみ: 大量保有報告書
  5,246 件、大量保有報告書（特例対象株券等）4,976 件、変更報告書
  31,175 件、変更報告書（特例対象株券等）21,054 件、

  230 訂正自己株券買付状況報告書 212 件。
- withdrawal_status は対象書類の全件で '0' であり、取下げの信号では

### 取れる信号（メタデータ）

- 公開買付系の原書類は全件が subject_edinet_code（対象者）を持ち、
  提出者コードも全件ある。方向の切り分けは parent_doc_id の連鎖で
  実測した: 270（公開買付報告書）は 594 件全件が 240 を親とし
  提出者・対象者が一致（提出者＝買付者、subject＝対象者）。
  310（対質問回答報告書）も 8 件全件が同方向（提出者＝買付者）。
  290（意見表明報告書）は検証可能な 476 件全件で、提出者が親の
  240 の対象者と一致し、subject が親の 240 の提出者と一致した
  （提出者＝対象者、subject＝買付者。残り1件は親書類が索引に無く
  連鎖で検証できない）。意見表明報告書は対象者が提出する書類で
  あること（制度の構造）とも一致する。
- subject が提出者自身と一致する公開買付届出書が 134 件ある
  （発行者による自己株式の公開買付け）。事実として自己関係を保持
  する（P2-T4 の自己組の扱いと同じ）。
- 大量保有系（350）は全件が issuer_edinet_code（発行会社）を持ち、
  提出者は保有者である。初回か変更かはタイトルの接頭辞
  （大量保有報告書／変更報告書）で決定的に切り分けられる。
- 自己株券買付状況報告書には issuer／subject は無く、提出者が
  買付を行う会社自身である。

### 内部 ID の解決（master/edinet_codes.parquet との照合）

- 提出者コードは3系統すべて全件解決した。公開買付系の subject も
  全件解決した。
- 大量保有の issuer は 571 件・201 コードが未解決だった。これらの
  コードは v1 索引の全期間で提出者として一度も現れず、会社マスタ
  の源泉（現行コードリストのスナップショットと v1 再構成の初期
  履歴）のどちらにも無い。発行会社としてのみ観測されるコードで
  あり、マスタ側の欠落として理由を記録し、行は
  related_internal_id を null のまま保持する（P2-T4 の未解決の
  扱いと同じ。マスタへの追加は会社マスタ側の工程の判断事項で、
  本チケットでは行わない）。

### 取れない信号

- 公開買付の条件（買付価格・株数・期間）、大量保有の保有割合、
  自己株券買付の取得株数・金額は書類本文（XBRL）の側にあり、
  メタデータには無い。P2-T4 と同じ切り分けで本文由来の構造化は
  行わず、器の列（event_date／split_ratio／effective_date）は
  null のまま残す。構造化はテキスト層の本格実装（別工程）の範囲。
- 自己株券買付の「買付プログラム」の同一性はメタデータからは
  決定的に判定できない（プログラムを指す識別子が無い）。月次の
  状況報告書をプログラム単位へ集約することはしない。

## 設計判断と根拠

- イベントの単位は書類（原書類1件＝イベント1件）とした。
  event_id は既存の決定的生成（doc_id と位置）に合わせ `#1` と
  する。臨時報告書のような提出事由の原子はこの3系統には無い。
- イベント種別は書類種別から決める: tender_offer_filing
  （公開買付届出）、tender_offer_withdrawal（公開買付撤回）、
  tender_offer_report（公開買付報告書）、tender_offer_opinion
  （意見表明）、tender_offer_qa_response（対質問回答）、
  large_holding_report（大量保有報告書）、
  large_holding_change_report（変更報告書（大量保有））、
  share_buyback_status（自己株券買付状況）。大量保有の初回／変更
  はタイトルの接頭辞で切り分ける（5種のタイトルすべてが実測で
  どちらかの接頭辞を持つ。接頭辞の無い将来の変種は変更側へ倒し、
  未知タイトルとしてサマリに数える）。
- 訂正書類（250・280・300・320・360・230）は新しいイベントと
  して数えず、系統ごとに件数だけをサマリに残す（P2-T4 の訂正の
  一本化と同じ方針。訂正の親は parent_doc_id で辿れる）。
- 関係先（related_edinet_code／related_internal_id）はメタデータ
  から決定的に取れる範囲で埋める: 公開買付系は subject、
  大量保有は issuer。自己株券買付は相手先の会社がメタデータに
  無いため null とする（自社株の買付であることは種別で表す）。
- 関係は relation_kind で意味を分ける: tender_offer は
  parent_* 側を買付者、subsidiary_* 側を対象者とし、意見表明
  報告書（290）だけ提出者と subject を入れ替えて
  （買付者→対象者）の向きにそろえる。large_holding は
  parent_* 側を保有者、subsidiary_* 側を発行会社とする。
  列名（parent／subsidiary）は器のスキーマを変えないために
  維持し、意味は relation_kind ごとに本記録とモジュールの
  docstring に明記する。親子関係（parent_subsidiary）と合わせ、
  関係の集約キーは (親側コード, 子側コード, relation_kind) と
  し、同じ組でも種別が違えば別の行にする。
- 関係の観測は原書類からのみ数える（訂正は観測にしない。
  P2-T4 と同じ）。公開買付では届出書と報告書と意見表明が同じ
  （買付者, 対象者）の組を複数回観測しうるが、組単位に集約する
  ため年表の重複にはならない。
- 既存の成果物を壊さないことの担保: 親子関係の集約は共通部品
  （_aggregate_pairs）へ切り出すが、P2-T4 分の出力が従来コードと
  実データで完全一致することを、着地前に旧コードとの差分照合で
  確認する（本記録の「実施結果」に結果を書く）。

## 配置について

- 配置の経路は既存の .github/workflows/company_events.yml
  （手動 dispatch、command は build のみ）で変わらない。build は
  入力全部からの冪等な再構築であり、本チケットの着地後に同じ
  ワークフローを dispatch すれば、既存分を含む全量が再構築され
  て配置される。マージ後の手順は P2-T4 と同じ: (1) ワークフロー
  を dispatch、(2) master/company_events_summary.json の件数が
  本記録の照合値（実行時点の索引による差を除く）と一致する
  ことを確認、の順である。
- 本記録の照合値は、同じプログラムをローカルで実行した結果で
  ある（入力は v1 索引の固定版と、配置済みの
  master/edinet_codes.parquet。generated_at のみ実行ごとに
  変わる）。

## 残件・限界

- 本文由来の構造化（公開買付の条件、保有割合、買付の取得状況）
  は未実施で、器の列は null のままである。テキスト層の本格
  実装（別工程）で扱う。
- 大量保有の issuer 201 コード（571 件）は会社マスタに無いため
  related_internal_id と関係の内部 ID が null である。マスタ側
  で発行会社のみのコードを取り込むかどうかは会社マスタ側の
  判断事項として残る。
- 日次の差分更新（v2 の書類目録からのイベント追加）の配線は
  P2-T4 と同じく本チケットに含めない。現行の build は入力全部
  からの冪等な再構築である。
- 自己株券買付状況報告書は月次の状況報告であり、イベントは
  報告書単位である。買付プログラム単位の集約（開始・終了の
  判定を含む）はメタデータからは決定的に行えないため行って
  いない。
