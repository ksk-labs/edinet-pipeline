## 作ったもの

- `pipeline/codelist.py`: 金融庁の固定 URL（https://disclosure2dl.edinet-fsa.go.jp/searchdocument/codelist/Edinetcode.zip）から EDINET コードリストを取得し、v2 データセットへ日次スナップショットとして保存して差分を生成する。
  - 取得: API キー不要（ダウンロードサイトの固定 URL）。429 / 5xx は hf_sync の `_with_retry` で指数バックオフ再試行する。応答が zip でない場合は恒常エラーにする。
  - 検証（形式の変更を静かに通さないため、すべて必須）: zip 内の CSV が1件だけであること、見出しが公式の13項目と完全一致すること、1行目の宣言件数と明細行数が一致すること、EDINET コードが一意であること、各行が13項目であること。
  - スナップショット（`codelist/date=YYYY-MM-DD/EdinetcodeDlInfo.csv`）: zip から取り出した CSV をバイト列のまま不変に保存する。日付は CSV 1行目の「ダウンロード実行日」（リスト自身の日付）で決める。取得実行日で決めないのは、金融庁側の公表が済んでいない早朝の試行が前日分を「当日分」として誤って確保することを避けるためであり、1日に複数回の試行（#29 で cron 化）ともこの形が整合する（公表前の試行は前日分の already_present になり、公表後の試行で当日分が確保される）。
  - 二重化（`codelist/archive/Edinetcode-YYYY-MM-DD.zip`）: 取得した zip そのものも別のパスへ保存する。抽出済み CSV と原形 zip の2形態を、別々のコミットで上げる。一方の保存が壊れても他方から復元・再抽出できる。ただし保存先は同一データセット内であり、データセット自体の喪失への備えにはならない（下記の未決事項）。
  - 差分（同日付の `diff.json` と `changes.jsonl`）: 前回成功したスナップショット（保存済みのうち日付が直近のもの）を基準に、EDINET コード単位で追加・削除・変更（項目ごとの旧値→新値）を記録する。値の正規化はしない（会社マスタ側の仕事。P2-T3）。初回は基準なし（base_date: null、全件が追加）。
  - 目録（`codelist/ledger.jsonl`）: 実行ごとの結果（ok・already_present・conflict・failed）を追記する。成果物を上げてから目録を上げる規律は塊1・塊2と同じ。取得・検証の失敗は例外で落とさず、理由つきの failed として目録と実行サマリに記録し、終了コード1で返す（ワークフローの失敗として監視に載る形）。
  - 冪等と競合: 同じ日付・同じ内容なら already_present として何も積まない。途中で中断した実行の再実行では、不足している成果物だけを補って完了させる。同じ日付で内容が異なる場合は競合として記録し、先に保存されたものを正として上書きしない（金融庁側の日中再生成や破損の兆候として監視対象に残す）。
  - 出所: スナップショットのメタ（snapshot.json）、差分、目録のいずれにも、源泉の種別・源泉側の識別子（固定 URL）・取得日時・再配布可否を持たせる（仕様 §3）。
- `.github/workflows/daily_codelist.yml`: 手動 dispatch のみ（入力なし）。schedule はコメントのまま置いた（有効化と複数回試行の配線は #29 の範囲。コメントには 09:15 / 15:15 JST の2回試行の形を残した）。証跡として目録と実行サマリを artifact に上げる。
- `tests/test_codelist.py`: 後述。

## 実取得で確定したこと

- zip の中身は `EdinetcodeDlInfo.csv` 1件のみ（2,311,469 バイト）。一次情報照合（files/2026-11-17-primary-source-checks.md）で未確認だったファイル名が確定した。
- 実ファイルは 2026-11-17 分で宣言件数 11,468 件、明細 11,468 行、EDINET コードは全件一意、全行13項目だった。
- 文字コードは公式表記どおり Shift_JIS 系だが、厳密な shift_jis では復号できないバイト（0xfb）が実ファイルに含まれるため、復号には cp932 を使う（実測で確定）。

## 試験と実測

1. **単体テスト（tests/test_codelist.py、16件）**: 検証（宣言件数の不一致・見出しの不一致・コード重複・CSV 欠落・非 zip をすべて失敗にする）、差分計算（追加・削除・項目単位の変更、同一なら空、初回は全件追加）、実行（初回の保存一式、再実行の冪等、翌日分の差分の実物照合、競合で先行分を保持、取得失敗と検証失敗の目録記録、中断後の再実行で不足分を補完）。全件合格。
2. **全体の回帰**: リポジトリのテスト一式（discovery・parse・codelist の計39件）が合格した。
3. **実ファイルの煙テスト**: モジュール自身の取得関数で実 zip を取得し、解析（11,468行、宣言日 2026-11-17）と、偽 HF への保存一式（成果物5点のアップロード、changes.jsonl 11,468行、目録への ok 記録）と、再実行の冪等（already_present、追加アップロードなし）を実物で確認した。HF への実アップロードは HF_TOKEN がローカルに無いため行っていない（実地確認は着地後の dispatch が担う）。

## 残した未決事項

- 二重化の範囲: 本実装の二重化は同一データセット内の2形態（抽出済み CSV と原形 zip）であり、データセット自体の喪失には備えていない。別系統の保存先（別データセットや GitHub 側）まで広げるかは、HF_TOKEN のスコープ（現行は financial-lakehouse-v2 のみ）に関わるためメインの判断事項として残す。
- cron のスケジュール有効化と、失敗・競合・スナップショット欠落の警報は #29（S2-T5-4）の範囲。本実装では失敗がワークフローの失敗と目録の failed 行として表面化するところまで。
- 会社マスタへの履歴反映と分類体系の版管理は P2-T3（#18）の範囲で、本チケットでは行っていない（13項目はそのまま保存済み）。
