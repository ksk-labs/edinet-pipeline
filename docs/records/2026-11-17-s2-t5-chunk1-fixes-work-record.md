## 修正内容

### S-1（must-fix）: 種別ごとに最初の1ディレクトリしかアップロードせず、目録は全件 ok と記録する

- 根本原因: ダウンロード済みファイルの置き場所を「種別 → ディレクトリ」の辞書で保持し、最初に登録された1ディレクトリだけがアップロード対象になっていた。一方、取得目録の ok 行はダウンロードできた全書類分が書かれていた。
- 修正: 保持の単位を「保存先ディレクトリ（repo 側パス）→ ローカルのディレクトリ」に変え、現れた全ディレクトリをアップロードする。あわせて、目録の ok 行はアップロード後に遠隔のファイル一覧を取り直し、実在を確認できた分についてだけ書く。確認できない分は `error_kind: upload_unconfirmed` の failed 行として記録し、次回の実行で再取得される。モジュールの不変条件「目録が ok を主張して実体が無い状態にはならない」を、書き方の注意ではなく処理の構造（ok は遠隔確認の後でのみ書く）で守る形にした。

### S-2（must-fix）: 書類取得 API の HTTP 200＋JSON エラー（429 を含む）をボディの StatusCode で判定していない

- 修正: `_get_once` で、HTTP 200 の応答ボディが JSON エラー応答（トップレベルに `StatusCode` を持つ）であればその値で判定する。429・5xx は `_RetryableHttpError` として再試行の経路に乗せ、それ以外は `EdinetError`（恒常的な失敗として書類単位で隔離）にする。判定は Content-Type に依存しないため、エラー JSON が JSON 以外の Content-Type で返っても本文が原形として保存されることはない。一覧 API の応答にも同じ判定が効く。
- あわせて保存前の形式検証を `fetch_document` に入れた: zip 系（type=1・3・4）は先頭が `PK`、PDF（type=2）は `%PDF` で始まることを確認し、合わない応答は EdinetError にして保存しない。

### S-3（should-fix）: 実行サマリが月単位の単一ファイルで上書きされる

- 修正: 保存先を `acquisition/month=YYYY-MM/run_summary-<対象日>-<実行開始時刻>.json` に変え、実行単位で残す。同月の後続の実行で上書きされない。ローカルの `out/run_summary.json` は従来どおりで、ワークフローの artifact 経路は変えていない。

### T-1（should-fix）: バナーコメント3件

- コメント規約に従い、区切りのバナーコメント3件を除去した（区切りは空行と定義の配置で足りる）。

### T-2（should-fix）: `_with_retry` の重複と再試行対象の食い違い

- 修正: discovery 側の再実装を削除し、`pipeline.hf_sync` の `_with_retry` を共用にした（EDINET 側・HF 側の両方）。判定を揃えるため、hf_sync の `_retryable` が例外の `response.status_code` に加えて `status_code` 属性も見るよう一般化し、discovery の `_RetryableHttpError` は `status_code` を持つ形にした。一般化は既存の例外型（response を持つもの、OSError、通常の例外）への判定結果を変えないことをテストで確認した。「hf_sync と同じ方針（対象と間隔）」という実態と異なる docstring は、関数ごと無くなった。

### T-3（should-fix）: `JsonlLedger` と batch.Ledger の重複 — 見送り（メインの判断に上げる）

- 理由: 寄せ先は JsonlLedger 側が自然だが、batch.Ledger はバックフィル本番（hf_sync の fetch/push と cli）が依存しており、`attempts` の数え方や `is_done`（入力ハッシュ＋シャード実在の判定）など意味が分岐している。統合は batch 側の振る舞いを変えるリスクがあり、並行して進む塊2 とも領域が近い。この修正では触らず、統合は「batch.Ledger を JsonlLedger の特殊形にする作業」として、バックフィルの回帰確認とセットで別途行うのが安全と判断した。
