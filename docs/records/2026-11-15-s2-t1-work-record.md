## 設計の要点

- 目録: 処理済みは `ledger.jsonl`（JSONL 追記）で管理し、doc_id ごとの最新行がその書類の状態を表す。
- 冪等: 「目録が ok で、入力 zip の SHA-256 が目録の記録と一致し、出力シャードが実在する」ときだけ処理済みとして飛ばす。入力が変われば再変換する。
- 再開: 出力は書類ごとのシャード (`silver/<doc_id>.parquet`) とし、一時ファイルから原子的に置いてから目録へ1行追記する（flush + fsync）。途中で止まっても目録にある分は次回そのまま使える。目録の壊れた行は読み込み時に無視する（追記は末尾にしか起きないため、壊れるのは最終行だけである）。
- 失敗の隔離: 書類単位で例外を捕捉し、`status=failed` と理由（tar_missing / zip_not_in_tar / tar_unreadable / bad_zip / convert_error）つきで目録へ記録して次へ進む。失敗した書類は次回の実行で自動的に再試行する。
- 系譜: 訂正の系譜は索引全体から作る。同一の親への訂正が複数ある場合（索引内に826件）、`superseded_by` は提出日時が最も新しい訂正を指す（本番規則。確定値は最新の訂正で決まるため）。
- 入力: 索引 parquet からジョブを生成する（提出日の範囲・doc_type・XBRL 有無で絞り込み可能）。ジョブ CSV からの指定もできる。書類 zip は日別 tar の中にあるため、tar 単位でまとめて1回だけ開く。

## 実測（受け入れ条件の確認）

### 1. 標本29書類の回帰

- 本番バッチ: 29件すべて ok、結合 21,079行。
- 試作の確定値（`prototype/output/silver_sample.parquet`、SHA-256 `b6fc90b354c0b5a9866f5b183db97778994035babc6e4872eba6ac08702a2559`）との比較結果:
  - 受け入れキー（書類・要素・期間・次元・単位・値）の多重集合: 完全一致（差分0行）。
  - 共通する全列の多重集合: 完全一致（差分0行）。
- 本番の結合ファイルの SHA-256 (`1fee0c3f39a2805539490c267e6c176dee2c8d82b352a4f84598c85004b0ced6`) は試作と異なる。理由は列構成の違い（試作の標本専用列 `cell` を本番スキーマに含めない）であり、行の中身は上記のとおり完全一致した。

### 2. 途中停止と再開（標本）

- `--max-docs 10` で区切って停止: 10件処理、結合 3,628行。
- 同じ状態で再実行: 10件スキップ + 19件処理、結合 21,079行。SHA-256 は全件実行時とバイト一致 (`1fee0c3f…`)。
- さらにもう一度再実行: 29件すべてスキップ、結合は不変。目録は29行（書類ごとに1行のみで、再実行による重複記録なし）。

### 3. 失敗の隔離（標本 + 実在しない書類2件）

- tar 内に zip が無い書類と、tar 自体が無い日付の書類を混ぜて実行: 実在の29件はすべて変換され、2件は理由つきで目録に failed として記録された（`zip_not_in_tar` / `tar_missing`）。結合は 21,079行で不変。
- 再実行: 29件スキップ、失敗2件は再試行され `attempts=2` で再記録。結合は不変。

### 4. 実地の1日分（2026-10-28、索引モード、全 XBRL 書類177件）

- 初回: 175 ok / 2 failed。失敗2件 (S100Z37E、S100Z37F) は lxml の既定のテキストノード上限に当たる `convert_error` で、試作も同じ上限を持っていた（標本29書類に含まれていなかったため未発見だった）。失敗しても残りは最後まで処理された。
- 修正（パーサに `huge_tree=True` を指定、コミット `388b18b4`）後の再実行: 177 ok / 0 failed、22,747行。
- 修正が標本の結果を変えていないことは、標本回帰の結合ファイルが修正前後でバイト一致したことで確認した。

### 5. 強制終了と再開（2026-10-28、177件）

- 30件処理された時点でプロセスを kill -9: 目録は30行（最終行まで完全な JSON として読める）、シャード30件が残った。
- 再開: 147件処理 + 30件スキップで完走。最終の結合（22,747行、SHA-256 `7ddb054c397eded7022d764f0d67986104eca5b019774506fd37f51c1eb06888`）は、中断なしで実行した場合とバイト一致した。欠落も重複もなし。

### 6. GitHub Actions

- push のたびに走る smoke ジョブ（依存導入と CLI 起動の確認）: コミット `23808451`、`388b18b4` のいずれも success。
- workflow_dispatch で convert ジョブを実行（対象日 2026-10-28、`max_docs=20`）: 全ステップ success。HF (v1) から索引と tar を取得し、変換し、成果物を artifact (`silver-2026-10-28`、60,975 bytes) に保存した。
- artifact の中身そのものは、ダウンロードが署名付き URL へのリダイレクトになるため、この経路では直接読み戻していない。代わりに同じ条件をローカルで再現し、成果物の構成（目録20行、シャード20件、結合 1,276行）と総量が artifact の大きさと整合することを確認した。

## 申し送り

- 実行時間の支配項は tar の走査（メンバー一覧の読み取り）の I/O だった。標本29書類（tar 15件・計約11GB）の全件実行は約2.5分で、その大半が走査である。バックフィル (S2-T2) では日付範囲ごとに必要な tar だけを開く現行方式で進め、実測を見て判断する。
- `superseded_by` の「最新の訂正1件」を指す規則は、Gold の勝者決定（時点値/確定値）の実装と整合させること。
- 恒常的に失敗する書類は目録の `attempts` と `error_kind` で検出できる。バックフィルの全数照合 (S2-T2) では、failed が残っていないことを完了の確認に含めること。
