# P2-T5 Gold 生成 作業記録

作成: 2026-11-17。対象: Issue #20（P2-T5）、仕様 #15 §7・§8。
成果物: pipeline/gold.py、tests/test_gold.py、.github/workflows/gold.yml、
requirements.txt への pyyaml の追加。あわせて指標登録簿の拡張を
edinet-definitions の PR（「feat: 指標登録簿を Gold 初期セットへ拡張する」）
で行った。

## 設計判断と根拠

### 成果物の構成（v2 データセットの gold/ 配下）

- annual.parquet: 会社×決算期の横持ち。登録簿の指標列（初期15件＋
  基礎値＋実演の CAGR）に、期間月数・変則フラグ・market（'JP'）・
  上場区分・会計基準・訂正の系譜への参照（代表書類、訂正の有無、
  最新訂正の書類）を持つ。
- annual_basis.parquet: 指標ごとの採用区分（連結/単体）と採用要素の
  縦持ち。横持ちに区分の列を指標ごとに持つと列が倍になるため別表にし、
  「単体の値を連結と誤表示しない」をこの表で担保する。
- quarterly.parquet: 四半期・半期の累計期間の表（TTM 合成の材料）。
- dividends.parquet: 配当の事実（銘柄次元つき、期種別つき）。
- forecasts.parquet: 会社予想の事実型の器（スキーマのみ、行は作らない）。
- summary.json / state.json: 生成統計と、日次差分の透かし。
- snapshots/date=YYYY-MM-DD/: 日次スナップショットとしての版固定の複写
  （仕様 §9、決定台帳 D14）。

### 確定値と勝者決定

試作（Step 1 の prototype/build_gold.py）の規則を本番 Silver に合わせて
引き継いだ。(1) point_in_time='final'（訂正書類由来）を優先、
(2) 提出日時の新しいもの、(3) 格納順（月の昇順、ファイル内行順）で
先のもの。この規則により、同一親への訂正が複数ある場合は最新の訂正
1件が勝者になり、superseded_by の本番規則と整合する。

### 連結と単体

要素の事実は次元なし（連結）を優先し、無い場合は NonConsolidatedMember
（単体）を採用して basis に明示する。実測では、売上サマリのある書類の
約17%（2026-06 の標本で 388/2,302 件）が単体のみであり、欠損にすると
非連結会社が丸ごと落ちるため、明示つき採用を選んだ。配当と発行済株式数は
単体の様式でしか出ないため、登録簿の dimension_priority で単体を優先する。
セグメント等の次元の事実は採用せず、数えて summary に記録する。

### 要素の候補

- 候補の固定単位は会社×会計基準とした（試作は会社単位。基準変更時に
  系列が混ざらないよう、基準が同じ範囲で候補を固定する）。
- 会計基準は、その期の有報の索引値（accounting_standard）を優先し、
  無ければその期間の事実の要素構成から推定する（IFRS 版・米国版の
  サマリ要素の有無）。
- フリーキャッシュフローの材料（有形・無形の取得支出）は、合算要素を
  持つ会社と内訳要素で分かれる会社が併存し、両形式が同じ書類に
  併存しないことを実データで確認した（2026-06 の標本で併存 0 件、
  合算のみ 270 件）。登録簿の要素候補にリスト形式（合計）を追加して
  両形式に対応した。支出は Silver では負値のため、登録簿で -1 倍して
  支出額（正）として保持し、FCF = 営業 CF − 取得支出 と定義どおりに
  計算する。取得支出は本表由来で当期・前期しかないため、FCF の充足は
  直近の年度に限られる。

### 決算期と四半期

- 年次行は、フロー系事実の期間のうち月数 10 以上、または有報の対象
  期間であるものとした。変則決算（移行期の短縮決算）は有報の対象期間
  であることで年次行に入る。期間月数は暦月で計算し、12 でない行に
  変則フラグを立てる。
- 四半期表では、四半期・半期書類のサマリに再掲される前年通年の期間
  （12 か月）を除外し、累計期間（12 か月未満）だけを対象とした
  （標本で 2,084 行の混入を実測し、除外後に解消を確認した）。

### 取れる信号と取れない信号の切り分け

- 取れた: 初期指標15件のうち期中平均株式数を除く全件、基礎値の
  発行済株式数、配当の年間実績と中間実績（銘柄は主銘柄＝普通株式に
  結び、期末分は年間−中間の導出として is_derived を立てる）。
- 取れない（器に留め、登録簿と本記録に理由を明記した）:
  - 期中平均株式数: 標準タクソノミに該当する標準要素が存在しない
    （存在するのは平均臨時雇用者数という別概念のみ）。登録簿に
    要素なしで登録し、列だけを持つ。
  - 配当の内訳（通常・特別・記念）の分離: 剰余金の配当の表は行次元
    （Row1Member 等）でしか分かれておらず、行の意味はテキスト側に
    あるため数値事実からは決定的に同定できない。dividends の
    breakdown は unspecified とし、1株配当の指標も「年間実績
    （内訳を含む）」として定義に限界を明記した。増配年数はこの
    限界を引き継ぐ（特別・記念配当の開始・終了が増減配として
    数えられる場合がある）。
  - 配当の権利確定日と支払日: 日付は非数値のため Silver に入らない。
    列だけを用意して null とした。
  - 種類株の配当: 会社ごとの拡張要素で様式が異なり標準化できない。
    dividends の銘柄列は器として持ち、本チケットでは主銘柄分のみ
    生成する。
  - 会社予想の取り込み: 源泉は決算短信（TDnet）。事実型の器
    （源泉・発表日・対象期間・値・修正の系譜）のみを作った。
  - IFRS・米国基準の純資産: 「非支配持分を含む総額」に対応する
    サマリの標準要素が無いため欠損とし、意味の異なる要素で
    代用しない。米国基準の取得支出も様式が確認できず欠損。

### 増配年数の定義

分割調整済みの系列で数える。隣接期の比較で、発行済株式数が両期に
揃う場合は当期の配当を前期の株式数ベースに換算してから比較し、
株式分割・併合の機械的な変動を除く。同額は増配に数えず、配当が
欠損している年度は連続を切る。株式数の変化には増資・減資も含まれる
ため調整は近似であり、その旨を登録簿の定義に明記した。

### 登録簿の置き方

正本は edinet-definitions リポジトリ（非公開）。Actions の
GITHUB_TOKEN では他リポジトリを読めないため、実行は v2 データセット
上の写し（definitions/indicators.yaml）を使い、sha256 を summary と
state に記録して版を固定する。写しの同期は sync-registry コマンド
（bot の経路がある環境で正本を取得してから実行する）。

### 日次差分（update）

state.json に月ごとの透かし（行数と最大提出日時）を持ち、変化した月を
検出して、その月に現れた書類の会社だけを再生成して差し替える。
材料の収集は影響会社の書類がある月だけに絞る。順序は Silver 日次 →
Gold 日次（仕様 §7）。ワークフローは手動 dispatch の経路を用意し、
日次の定期実行への配線は Silver 側の運転観測と合わせた後続作業とする
（P2-T3 の update と同じ扱い）。

## 実測（標本: Silver の 2026-06 と 2026-11 の2か月分）

2か月分の入力からの生成（全期間の生成はマージ後の dispatch で行う）:

- annual 13,599 行（2,614 社）、quarterly 4,390 行、
  dividends 16,914 行、annual_basis 182,872 行。
- 指標ごとの充足（annual 13,599 行中）: EPS 12,440、BPS 12,373、
  自己資本比率 12,445、総資産 12,446、営業 CF 12,340、
  売上高 10,857、純利益 12,079、経常利益 11,527、純資産 11,539、
  1株配当 10,412、発行済株式数 12,366、営業利益 5,966、
  取得支出 3,784、FCF 3,781、期中平均株式数 0（器どおり）。
  営業利益と取得支出・FCF の充足が低いのは、本表由来で当期・前期
  しか取れないことと、標本が2か月分で各社の直近の有報しか無い
  ことによる。全期間の入力では有報が毎年揃うため充足は上がる。
- 未解決の書類は 0 件。セグメント等の次元で対象外にした事実は
  34,737 件、訂正で確定値が置き換わった事実は 183 件。
- 個別照合: スターシーズ（E03498）の最新期で、売上高・EPS・BPS・
  配当・発行済株式数・自己資本比率・ROE・営業 CF が Silver の
  実物と一致し、FCF の符号処理（営業 CF − 取得支出）も一致した。
- テスト: 新規 21 件を含む全 195 件が合格（CI で確認する）。
- update は、変化のない入力では「変化なし」を返すことを確認した
  （冪等）。透かしを人為的に古くした入力での変化検出と影響会社の
  再生成は、実行基盤の障害のため本記録の作成時点では未実施であり、
  復旧後に確認する（未確認のまま完了とはしない）。

## code-review 指摘の修正（2026-11-17、PR #44 のレビュー後）

レビュー報告書 files/2026-11-17-p2t5-code-review.md の指摘 3 件を修正した。

- MF-1（must-fix）: update の透かしに月 parquet の内容ハッシュ
  （sha256）を加えた。従来の透かし（行数・最大提出日時）では、
  既存書類の再解析で値だけが書き換わり行数と最大提出日時が変わらない
  場合に update が「no changes」で終わり Gold が無言で陳腐化する
  欠陥があった。レビュー側の最小実験で再現済みであり、修正役も
  同型の回帰テスト（test_value_only_rewrite_is_detected）で修正前は
  失敗し修正後は合格することを実測で確認した。あわせて、変化のない
  入力では update が「no changes」を返す回帰テストも追加した。
  state.json の透かしの形式が変わるが、Gold はまだ本番 build されて
  いないため移行は不要である。旧形式の state との比較では透かしが
  不一致となり一度だけ全月が変化として扱われ、影響会社が再生成される
  （冪等なため安全）。なお本節の修正により、上記の「透かしを人為的に
  古くした入力での変化検出と影響会社の再生成は未実施」という留保は、
  値の書き換えに対する変化検出と再生成の範囲で解消した。
- S-1: 勝者決定の同点時の決め手を doc_id に揃えた。従来は格納順
  （seq）だったため、同一 submit_at（分単位）の訂正が 2 件ある場合に
  勝者と系譜の latest_correction_doc_id が食い違う可能性があった。
  優先順は final → 提出日時 → doc_id の大きいもの → 格納順とし、
  build_doc_lineage と同じ順序にした。回帰テストで同一 submit_at の
  訂正 2 件の勝者が doc_id の大きい方になることを固定した。
- S-2: 代表書類 source_doc の選択を提出日時最大のものにした。従来は
  annual_docs の挿入順（docs[0]）で、提出日時順ではなかった。
  表示と出所の列への影響に限られる。回帰テストで固定した。
- テスト: 新規 4 件を加え、test_gold.py は 25 件、リポジトリ全体で
  199 件が全件合格（ローカルで実測。CI でも確認する）。

  登録簿に追加する。

  since-month の引き下げで取り込む。
