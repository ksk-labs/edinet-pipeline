## 再構成の設計

### 観測の集約

索引の各行を「提出日に、提出者（EDINET コード）について、証券コード・法人番号・
会社名が観測された」出来事として扱い、(EDINET コード, 種別, 値) 単位に集約する。
各集約行は初観測日・最終観測日・観測回数と、証跡として最初と最後の doc_id を持つ。
矛盾する観測（同一コードに複数の法人番号など）は上書きせず併記し、
観測回数で多数を判別できる形にする（仕様 §1）。

### 出力（v2 データセットの master/history_from_v1/ へ置く形。今回はローカル生成）

1. `identifier_history.parquet` — 識別子と名称の履歴。
   列: edinet_code, kind（securities_code / corporate_number / company_name）, value,
   source_value, value_normalized, change_key, is_placeholder,
   first_observed_date, last_observed_date, observation_count, first_doc_id, last_doc_id,
   出所5列（source_kind, source_dataset, source_file, source_file_sha256, generated_at,
   redistributable）。
   - 証券コードの value は `JP:` を除いた5文字とし、原形は source_value に保持する
     （コードリスト側の証券コードと突き合わせられる形にするため）。
   - `JP:00000` は value='00000'、is_placeholder=true とし、照合には使わない。
2. `code_roster.parquet` — コードごとの観測の台帳。
   列: edinet_code, first_observed_date, last_observed_date, document_count,
   distinct_name_count, distinct_jcn_count, distinct_securities_code_count, 出所5列。
3. `code_connections.parquet` — 法人番号の共有によるコード間の接続候補（確定候補のみ）。
   列: edinet_code_a, edinet_code_b, basis（corporate_number）, shared_value,
   rows_a, rows_b, strength, name_agreement, note, 出所5列。
4. `review_items.parquet` — 要確認の一覧（接続しないもの、矛盾、候補）。
   列: item_type, edinet_code_a, edinet_code_b, shared_value, detail, 出所5列。
5. `summary.json` — 件数の照合（対象コード数、各履歴の行数、接続と要確認の内訳）。

### 名称の正規化（仕様 §1 の規則の具体化）

- value_normalized: NFKC 正規化（全角・半角の統一、㈱等の互換文字の展開）→
  空白の除去 → 略記法人格（(株) 等）を正式表記へ統一。
- change_key（変更判定用）: value_normalized を小文字化（英字の大文字・小文字は
  表記ゆれとして扱う解釈。Robot Home の実例で確認）し、先頭・末尾の法人格
  （株式会社・有限会社・合同会社・合資会社・合名会社・社団/財団法人・医療法人・
  学校法人・社会福祉法人・特定非営利活動法人・投資法人・協同組合）を繰り返し除去。
- 実測: 複数の原名称を持つコード 640 件のうち、正規化後も変更キーで複数になるのは
  600 件（残りは実在の改称とみられる。例: 電通国際情報サービス→電通総研）。
- 履歴の値は常に原形（正規化前）を保持し、正規化は判定にのみ使う。

### 自動接続規則の適用（2026-11-17 精緻化の確定規則）

法人番号を共有するコードの組（実測 10 組）について:
- strength='strong': 共有する法人番号が両コードで 2 行以上観測され、かつ両コードの
  多数派（最大観測回数）の法人番号である。
- strength='corroborated': 片側の観測が 1 行だが、その法人番号が両コードの唯一または
  多数派の法人番号であり、正規化した名称が一致し、証券コードの矛盾が無い
  （他の属性との整合が取れる場合）。
- 上記以外は接続せず review_items に回す（item_type='jcn_link_needs_review'）。
  実測では E05335–E05348 の組が該当する（E05335 側は 20 行中 1 行だけの少数観測で、
  多数派の法人番号と食い違い、名称・証券コードも一致しない。既知の混入誤り）。
- 同一コード内の法人番号の矛盾（複数値）は review_items に回す
  （item_type='jcn_within_code_conflict'。実測 2 件: E05335、E30091）。
- 法人番号で結べない組のうち、正規化した名称（変更キー）が一致するコードの組は
  候補として review_items に回す（item_type='name_only_candidate'。未確定のまま残す）。
  実測は組（コードのペア）単位で 86 組・キー単位で 87 行（実施結果の節を参照）。
  なお探索段階の予備集計では「キーの側で数え、組の一部でも法人番号で結べるキーを
  除外する」別の数え方で 79 キーだったが、実装の数え方（ペア単位）とは単位が
  異なるため、成果物の件数としてはペア単位の値を正とする。
  証券コードを共有するコードの組は実測 0 件だった（プレースホルダ 00000 を除く）。

### 範囲外の明記

- 業種・所在地・上場区分・資本金・決算日は v1 索引から復元できない（現行値のみ。
  P2-T3 の範囲）。本再構成の対象に含めない（仕様 §3）。
- 内部 ID の発行と会社マスタへの統合は P2-T3 の範囲。本チケットは初期履歴と
  接続候補・要確認までを成果物とする。
- コードごとの「提出の立場」は P2-T3 で扱う（本再構成では導出しない）。

### 配置について

v2 データセット（Yoshi-Dai/financial-lakehouse-v2）への書き込み資格情報は
GitHub Actions のリポジトリシークレットにのみあり、この環境からはアップロード
できない。そのため成果物はローカルに生成し、配置先のパス（master/history_from_v1/）
を記録する。アップロードは P2-T3 の着手時か、日次自動化側の経路で別途行う。
